# Insight-Digest 명세 (단일 진실원천)

> 이 파일은 **paper-digest-composer**가 사용하는 readable 서문 명세다.
> 이 명세를 따라 "그 분야를 모르는 독자도 읽히는, insight·함의 중심" 단락을
> 생성한다. (주의: 별도 스킬 `paper-digest`는 이 파일을 참조하지 않는 독립 구현이다.)

## 구조 (4 + 2)

1. **Context** — 문제는 무엇인가? 왜 중요한가(비전문가 기준)?
2. **Insight** — 이 글이 남들이 놓친 무엇을 깨달았는가?
3. **Solution** — insight가 방법/주장으로 어떻게 자연스럽게 이어지는가?
4. **Evidence** — 작동/타당함을 보여주는 구체적 비교(숫자가 있으면 출처 표기).

그다음:
- **Implication** 한 줄 — insight의 함의(이게 열어주는 가능성/바뀌는 것).
- 출처 링크(있으면): arxiv면 `📎 https://arxiv.org/abs/{id}`, 그 외 원문 URL.

## 작성 규칙

- 독자는 똑똑하지만 해당 도메인에 익숙하지 않다고 가정한다.
- 구체적 비유·예시를 쓴다 ("쓰레기통 역할" >> "특정 토큰에 집중").
- 인과 사슬을 명시한다 (X 때문에 Y가 일어남).
- 대안과 비교·대조한다 ("X는 실패했으나 Y는 성공").
- 핵심 개념 **2-4개**를 굵게 표시한다.
- 전문 용어는 첫 등장 시 `용어(간단 설명)` 형식.
- 사용자 입력 언어와 일치(Korean/English). 구조는 언어와 무관하게 동일.

## 피해야 할 것

- 직관 없는 전문용어.
- 대안 비교 없는 결과 서술.
- 동기 없는 방법 설명("이렇게 했다"만, "왜 그랬는지" 누락).

## 다중 문서 처리

- 통합 주제·문제로 시작.
- 각 문서가 서로 다르게 깨달은 바를 대조.
- 문서 간 함의를 종합.

## composer 확장

composer는 위 4+2 서문에 더해 다음을 생성한다:
- **Limitations** — 저자/원문 인정 한계 + 독자 식별 한계.
- **Open Questions** — 열려 있는 미해결 질문.
이로써 composer의 산출은 CISELQ(Context/Insight/Solution/Evidence/Limitations/Open)가 된다.
